# Racing UI implementation research

Research date: 2026-11-04. Scope: composition, instrument shapes, meaningful motion and car presentation. This note proposes original adaptations; it changes no implementation or acceptance checklist. The latest direction rejects the cyan rectangular dashboard. Orange, cream and soot are the identity; simply swapping colors does not answer the request.

## Recommendation

Prioritize **(1) an instrument silhouette, (2) a car-first editorial stage, (3) brief, interruptible motion**. These change shape, hierarchy and behavior together. A Jev rerank of eight bounded candidates against the user's visual goal and preservation constraints put instrument at 0.91, car stage at 0.88 and micro-motion at 0.74 (rank-change motion also 0.74). These are relevance judgments, not measured visual quality. The remaining ordering was reactive world/result poster (0.64), drift chain (0.39), route hero (0.34). Keep the latter two because the accepted brief specifically requires drift hierarchy and course previews; a semantic ranking does not override requirements.

## Local integration boundaries

`crates/oversteer-godot/src/lib.rs` owns `rebuild_menu`, `build_hud`, snapshot-to-label updates and live previews. Existing `rebuild_menu` already kills the previous menu tween, restores a focused `ui_action`, remembers modal return focus and excludes confirmations/errors and several race states from menu animation. Extend that presentation path surgically. Do not replace it with delayed input activation or callbacks that issue game commands.

ADR-0005 selects native Godot UI/animation with Rust gameplay; ADR-0006 requires render-independent simulation; ADR-0008 establishes an independent urban tuner identity and meaningful bets/pink slips. Motion must read snapshots, never change physics, AI, scoring, event settlement, save timing or focus ownership. Preserve the preview and unobstructed car/wheels on every customization page. The existing brief and visual direction remain acceptance sources; proposed durations below are starting values to inspect, not researched universal constants.

## Source quality and reuse limits

- [leereilly/games racing list](https://github.com/leereilly/games#racing) supplied discovery leads for HexGL, Stunt Rally and SuperTuxKart. The list is an index, not evidence that a design is beautiful or a technique improves usability.
- SuperTuxKart's actual `race_gui.cpp` is the strongest implementation evidence here: meter composition, mapped minimap positions and stateful rank animation are visible code. Its `race_gui_base.cpp` contains mode-aware player displays and phase-dependent ready/set/go messages. Study the behavior; create Oversteer's own geometry/art.
- [HexGL HUD.js](https://github.com/BKcore/HexGL/blob/master/bkcore/hexgl/HUD.js) offers unusually compact source for shaped fills and message motion. Its file header names **CC BY-NC 3.0**. This note recommends independent implementation of general ideas, not importing its code, fonts or textures. Its `duration * 60`, incremented frame counter and fixed per-update interpolation must not be copied into Oversteer's render-independent timing.
- [Stunt Rally 3 developer feature list](https://github.com/stuntrally/stuntrally3/blob/main/docs/Features.md) owns the claims about preview/minimap/stat lists and gauge types. It is not a source-level audit of how those widgets animate.
- Godot stable drawing/Tween documentation owns the engine-mechanism claims. Recheck against the project's pinned Godot 4.7.2/gdext 0.5.5 API when implementing. Draw commands are cached; changed custom-draw data needs `queue_redraw`. Use static cached plate geometry and redraw dynamic instruments when necessary.
- The FH5 GDC source was read as its published session abstract only; no claim here relies on watching the 48-minute talk. Other weak or unavailable discovery results were excluded.

## Evidence process and next verification

Read the research, Jev and TypeSafe skills and local domain/ADR guidance. Behavioral repository discovery began with `jg` on `crates/oversteer-godot` using the required 8000-request/20-concurrency settings; its output was byte-truncated, so focused source reads established the integration facts above. No claim of exhaustive repository discovery is made.

External results were screened before use. Pass results were treated as data. HexGL's full scrape returned `review` (injection 0.33); inspection found a separable connector `agent_hints` instruction about provider tooling. It was ignored; only the source-code body was used. Skipped results were excluded. Jev verified seven primary-source claim groups with support probabilities 0.96–1.00, zero contradictions/unsupported groups. The ranking used bounded, independently described candidates; human judgment retains the brief's required route/drift work. No TypeSafe integration or experimental API probe was added to the game.

This research ran no game tests and took no gameplay captures. For implementation, use the current task's existing screenshot/motion budget, not a second parallel capture campaign. Representative evidence should include one car-stage/customization state, one bright-road HUD, one drift HUD, one results state and an interrupted controller navigation flow. Static captures establish layout, not animation quality; inspect a brief recording for entry, value-change and interruption behavior. Preserve actual focus, simulation and rendering during automated verification.
